Bid Pipeline — Agent Team Architecture




  Bid Pipeline — Agent Team Architecture
    Oct 7, 2026         · ​@Scott Turner


  The rule
  No number reaches a bid document unless it points at a page, sheet, photo, clause or field
  measurement that a human can open and check. An agent that cannot cite writes FIELD
  and moves on; it never estimates, never fills from training memory, never rounds a scaled
  dimension into a dimensioned one. The auditor agent enforces this mechanically: a figure
  without a ledger entry is a build failure, not a warning.

  Three corollaries shape everything below:

   1. The source documents are the only ground truth. Codes, product data sheets and unit
      prices are fetched and cited, never recalled.
   2. Gaps are a deliverable. A list of what the crew must measure and what the owner must
      answer is as much the output as the scope itself.
   3. The job type is discovered from the documents, not told to the system. The same team
      bids a pier, a window swap or a silo repaint because the team is organized by what a bid
      needs, not by trade.

  Pipeline at a glance




  bid pipeline · 10 agents, one ledger, one gate

  Readers turn each source type into ledger rows; specialists add quantities, codes,
  materials and customer instructions as more rows; the Scope Writer renders only from
  rows, and the Auditor opens every cited source before the bid leaves. A figure the Auditor
  cannot trace goes back to the ledger as an orphan, not to the customer.


  Agent roster
  Ten roles. The orchestrator spawns only the specialists a job's documents call for, so a silo
  repaint runs fewer agents than a pier. Every agent writes to the shared claim ledger and
  nowhere else; the scope writer and the auditor read only the ledger.

  Pricing is deliberately a later agent: it reads Mersco's own rate book and labor factors, and
  every unit price it applies must cite a rate-book line the same way a quantity cites a
  drawing.


  The claim ledger
  The ledger is one append-only table per job. Every figure that could appear in a bid — a
  count, a length, a product name, a spread rate, a code section, a customer instruction — is
  a row. The proposal is rendered from rows; a figure typed directly into the proposal is an
  orphan and fails audit.

  Method rules the auditor enforces

         dimensioned and counted may feed a Mersco allowance as stated.
         scaled must say so in the proposal text and carries a FIELD-verify note; it never
        becomes an order quantity without a site check.
         observed (from a photo) may name a condition and a location; it may never carry a
        number.
         fetched must store the URL and the retrieval date; a dead link at audit time is a fail.
         customer captures an instruction verbatim with the message date; it cannot override
        a spec clause, only sit beside it as a flagged conflict.
         FIELD is a legitimate row: value blank, statement says exactly what to measure. The
        proposal prints it as "FIELD" inside the allowance parenthetical, which is what the two
        test bids do.

  Prove-your-work output: alongside the proposal the pipeline emits the ledger as a
  spreadsheet and a cross-reference view — every paragraph of the proposal listed with
  the claim IDs it draws on. A reviewer can click from any number to the page image it came
  from.



  Job-agnostic design
  The team never needs a "painting mode" or a "pier mode" because nothing in it is keyed to
  a trade. Four design choices make that hold.

  CSI MasterFormat is the spine. Mersco already writes proposals by division (01 General
  Conditions, 03 Concrete, 05 Metals, 07 Thermal & Moisture, 09 Finishes, 31 Earthwork, 35
  Waterway & Marine). The Intake agent tags each source page with the divisions it
  touches; the orchestrator spawns one Takeoff and one Materials pass per division
  present. A pier bid lights up 31, 33 and 35; a silo repaint lights up 09 and 05; a condo
  window job lights up 08. The proposal template is the same file every time.

  Source types are the plug-in boundary, not job types. A reader exists per kind of
  document (drawing, spec, photo, correspondence, schedule, spreadsheet, RFP). A new
  job with an unfamiliar document type (a marine survey, an NRCS silo report, a window
  schedule) adds a reader, not a new pipeline.

  Codes are looked up by address and division. The Codes agent takes the job address,
  resolves the AHJ and adopted code edition for that jurisdiction, and fetches the sections
  the detected divisions trigger. Florida (FBC), Maryland (IBC with state amendments) and
  Delaware all resolve the same way. Marine, agricultural and multifamily overlays (USACE
  permits, grain-handling OSHA 1910.272, FHA/condo rules) come from the same lookup,
  keyed by division and site type, with URLs stored in the ledger.

  Customer requirements are a layer, not a rewrite. Chris's "keep the base bid simple"
  instruction, an owner's warranty choice, a PM's phasing note — these are customer rows
  that shape the base-vs-alternate split and the proposal's emphasis. They never change a
  spec figure. When they conflict with a spec, both rows print under Open Questions, which
  is how the Ocean Beach bid handles the garage doors and the missing deck-coating
  product.

  What changes per job is therefore only the packet. What stays fixed is the ledger schema,
  the division template, the audit rule and the agent roster.

  Codes are cached as evidence, never as conclusions. The two lookups on the test jobs
  cost a third of the session, so reuse is tempting, but codes, permit pages and product
  lines change. The discontinued Hilti HIT-HY 70 is the warning: a cached row naming it
  would have looked traceable and been wrong. The Codes agent therefore keeps a per-
  jurisdiction cache of fetched pages (URL, retrieval date, content hash, quoted clause, and
  the edition or effective date the page states), and the Auditor applies a freshness rule
  before any cached row may feed a bid:

  One consequence to accept up front: observed rows from photos and scaled rows from
  undimensioned details are inherently judgment calls. They are allowed to vary between
  runs, which is exactly why they can never carry an order quantity.


  Permissioning
  Each agent is a service principal with one role and the minimum access that role needs.
  No agent sees everything, no agent can edit history, and the only principal who can
  release a bid is Chris. Readers process untrusted documents, so they get no network and
  no free-text channel: a PDF or email carrying injected instructions has nothing to call out
  with and no way to talk to the orchestrator except through the schema.

  How it is enforced

        Each agent runs with its own allowed-tools list in the Agent SDK and its own filesystem
        scope: a container per role, or a single broker process that is the only thing with write
        access to the ledger and checks the caller's role against the method it is trying to write.
        The Orchestrator can spawn agents and read their status. It cannot write ledger rows
        and does not see document content, only the Source Register.
        Secrets (API keys, rate book path) live in the broker's environment, never in a prompt
        or a tool result.
        Document content is data. Reader prompts state it; the schema enforces it; the
        missing network makes it moot.
        Every access is logged with the principal, so a bad row can be traced to the agent and
        the call that produced it.

  Human roles

        Chris: release authority, rate book owner, approves prompt changes, answers
        unverified escalations.
        Field crew: fills FIELD rows through a form that writes measured rows with the
        person's name and date. They cannot change anything else.
        Engineer or owner: never touches the system; their answers are entered by Chris as
        customer rows with the message date.



  Model tiering and cost
  The pipeline is designed to run mostly on Haiku, with Sonnet where a task needs to hold
  two things in mind at once. A small model is reliable when it is never asked a question with
  two reasonable answers, so the frugality work is really ambiguity-removal work.

  Ambiguity-removal rules every prompt carries

        One unit of input per call (a page, a tile, a photo, a URL). No accumulated conversation;
        every call is stateless.
        Output is the schema or nothing. Fields that are not stated in the input are null .
        "Probably" is not a value.
        Enumerated vocabularies for division, method, unit, condition and confidence. The
        model picks from a list; it does not name things.
        Two or three examples from the golden jobs in every prompt, chosen to show the null
        case as well as the filled one.
        No multi-step reasoning asked of Haiku. A task that needs two steps is two calls.

  Cost controls

        Redundancy before escalation: three Haiku passes with field-level voting cost less
        than one frontier pass and produce a disagreement signal a single pass cannot.
        Prompt caching on every system prompt; contexts kept small so the cached share
        dominates.
        Code does everything code can do: text layers, OCR, contact sheets, drawing tiles on a
        fixed grid, link checks, arithmetic.
        Per-jurisdiction and per-manufacturer caches with the freshness policy above: the
        search is skipped, the fetch is not.
        Cost per bid is a ledger field (tokens by agent, by model, in dollars), so Chris sees what
        a bid cost to produce against what it is worth.

  For scale: producing the two test bids interactively with a frontier model cost about 8.5
  million weighted tokens, a third of it in the code lookups. A pipeline of stateless Haiku
  calls on the same packets should land at a small fraction of that; the golden-test runs in
  Phase 1 will give the real number.

  Build plan
  Build the ledger and the auditor first; they are what make the system trustworthy, and
  every other agent is replaceable once they exist.

   1. Ledger + Intake + Auditor (foundation). Define the ledger schema as a SQLite store
      per job, written only through a broker that enforces the access matrix (append-only,
      method scoped by role, versions stamped on every row). Check the two test packets in
      as golden fixtures. Intake builds the Source Register with hashes and page images.
      Auditor opens a cited page and confirms a value. Test: feed it the two hand-written
      bids above and have it find every orphan.
   2. Drawing, Spec, Photo and Correspondence readers. Each is a Claude Agent SDK
      subagent with a narrow system prompt, read-only file tools, and one output: ledger
      rows. Re-run on the Nantucket and Ocean Beach packets; the rows must reproduce
      the figures in the two bids.
   3. Takeoff and Customer Requirements. Takeoff carries the derivation rule; Customer
      Requirements carries the base-vs-alternate split. Scope Writer renders the Mersco
      template from rows.

   4. Codes & Regulations and Materials. Web-fetching agents with URL-and-date storage.
      Start with the three jurisdictions Mersco is licensed in (FL CGC, MD MHIC, DE) and
      the manufacturers in the current spec pool (Sherwin-Williams, Sika, Hilti, Euclid).
   5. Pricing. Only after the above are audited clean on five real jobs. Mersco's rate book
      becomes a Source Register entry like any other.

  Stack

        Orchestration: Claude Agent SDK with subagents per role; the orchestrator holds the
        plan, subagents hold narrow context.
        Skills: one skill per reader type and one for the Mersco proposal template, so a new
        document type or a template change is a skill edit, not a code change.
